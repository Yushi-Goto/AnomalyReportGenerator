# 概要
このチケット及び対応ブランチでは、[システム概要](https://github.com/Yushi-Goto/AnomalyReportGenerator/wiki/%E3%82%B7%E3%82%B9%E3%83%86%E3%83%A0%E6%A6%82%E8%A6%81#%E3%82%B7%E3%82%B9%E3%83%86%E3%83%A0%E6%A7%8B%E6%88%90%E3%82%A2%E3%83%BC%E3%82%AD%E3%83%86%E3%82%AF%E3%83%81%E3%83%A3)の「VLM」コンポーネントを開発する。
具体的には以下のAPIエンドポイントを実装する。
- /anomaly/explain

# APIエンドポイント（調整中）
## APIエンドポイント一覧
| エンドポイント   | 入力                                                                                                                                                       | 出力                            | 
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | 
| /anomaly/explain | request_id: キャッシュ情報参照用のID     | ~~text: 説明文~~ JSON

## 1) `/anomaly/explain`の想定用途
■目的
- 視覚的根拠を言語化
- 最終的な現場判断を支援する

■ユースケース
- 人間の目視で異常の判断が難しい場合 / 時間がかかる場合
- 説明性の向上（JSON Schema で項目をまとめる）
- 誤検知のでバック速度向上
- 人間が最終判断する際に、説明性を補助

■要点
- 終点エンドポイント
- トークンを消費することに注意

# システム全体のフロー
### ステップA：一次判定（自動）
`/anomaly/predict` → スコアで OK/NG

（ここで、次のステップBでヒートマップ画像を作成するために「推論結果」「リサイズした元画像」「異常マップ画像」をTTLキャッシュとして保存しておく）

### ステップB：根拠提示（人の確認）
NGや保留のときだけ `/anomaly/heatmap` → 可視化で「どこが異常か」

（ここで、次のステップCで説明文を作成するため「ヒートマップ画像」もTTLキャッシュに加えておく）

### ステップC：説明（文章化・報告書化）
`gpt/explain` → 入力：(predict のスコア/ラベル +) 元画像 + ヒートマップ重畳 ~~+ パッチ~~、出力：現場向け所見、確認ポイント、誤検知の可能性





# 各エンドポイントについてのルールと使い方
## ルール
### ルール1：404は「request_idが無い/期限切れ」のみ
- `/anomaly/heatmap` も `/anomaly/explain` も **request_idがキャッシュに無いなら404**
- 逆に、キャッシュにあるなら派生物はサーバが作る

### ルール2：fileフォールバックは「開発・デバッグ用途」
- 本番想定ではOFFがいいかも
- もし残すなら、READMEに「デバッグ用」と明記する

## 使い方
- `POST /anomaly/predict` は推論を行い、`request_id` を返す（TTLは5分）
- `POST /anomaly/heatmap` は `request_id` を必要とし、キャッシュが無い場合は 404 を返す
    - デバッグ用に `file` を渡した場合のみ単発推論で生成する
- `POST /anomaly/explain` は `request_id` を必要とし、キャッシュが無い場合は 404 を返す（フォールバック無し）
    - ここもデバッグ用に `file` を渡してフォールバック処理してもよいと思う（後回し）

※追記：デバッグ用だからと言ってフォールバック処理させすぎると何でも屋になってしまってよいないかも。





# VLMモデル選定
画像理解力、日本語表現力、JSON安定性、コストの観点から、一旦は `GPT-4o` を利用する。





# VLMの出力形式（JSON Schema）について
OpenAIのstructured outputs（JSON Schema）で出力形式を固定する。
↑その方が最終的な評価もやり易そう。

## ■JSON Schema の項目
| No. | 項目名（型）                                                     | 意味                                                                                                                         | 狙い                                                                            | 評価方法                                                                        | 
| --- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | 
| 1   | has_anomaly（boolean）                                           | 異常があると判断したか（true/false）                                                                                         | まず大枠の判定を固定。あとで「誤検知/見逃し」分析の軸になる。                   | 正解ラベルがあるなら accuracy 系、ないなら「異常スコア閾値との整合」など        | 
| 2   | location（string）                                               | 異常の位置（例：「画像右上の角付近」「中央の円形部品の縁」）                                                                 | 「どこが変か」を必ず言わせる。説明の“芯”になる。                              | 後でやりたい 異常部位言及率（部位キーワード一致/類似度）に直結                  | 
| 3   | appearance（string）                                             | 異常の見え方（例：「黒い汚れ」「欠け」「ずれ」「傷」「色ムラ」）                                                             | 位置だけだと弱いので、「どう変か」も固定して言わせる。                          | 異常タイプ別の傾向分析、説明の多様性/一貫性（同じ異常に同じ語彙が出るか）       | 
| 4   | evidence_from_heatmap（string）                                  | 意味：**ヒートマップ（重畳）を根拠にした説明**（例：「赤/高反応が右上に集中しているため…」）                                | VLMが“それっぽい作文”をしないように、**必ず根拠をヒートマップに結びつける**。 | 根拠言及率（「ヒートマップ」「赤」「高反応」等の用語）や説明の妥当性チェック    | 
| 5   | hypotheses（string[]）                                           | 推定原因の**仮説リスト**（0〜3件くらい）<br>例：`["汚れ付着", "印刷不良", "欠損の可能性"]`                                   | 原因は確定できないので **「仮説」**として限定し、過剰な断定を抑える。           | 現場知見がある場合に「仮説の妥当性」レビューがしやすい / 文章比較もやりやすい。 | 
| 6   | checks（string[]）                                               | 次に取るべき確認手順（0〜5件くらい）<br>例：`["該当箇所を拡大して目視確認", "別角度の画像で再撮影", "良品と並べて差分確認"]` | 実務っぽい価値が出る部分。**「アクション」**に落とせる。                        | 説明の有用性評価（手順が出るか、具体性があるか）                                | 
| 7   | false_positive_risk（enum: "low" &#124; "medium" &#124; "high"） | 誤検知の可能性の自己評価                                                                                                     | 不確実性を固定フォーマットで出させる（安全設計）                                | 閾値付近の画像で “high” が増えるか、スコアと相関するか等を分析可能。          | 
| 8   | notes（string, optional）                                        | 補足<br>例：`「照明反射の影響の可能性」「背景模様に引っ張られているかも」`                                                   | スキーマを増やさず、でも言いたいことが溢れた時の逃げ道として用意しておく。      | 後から分類したくなった項目の元ネタになりそう（ログとして強い）。                | 

## ■出力例
```
{
  "has_anomaly": true,
  "location": "画像右上の角付近",
  "appearance": "白っぽい欠け/剥がれのように見える",
  "evidence_from_heatmap": "重畳ヒートマップで右上に高反応が集中しており、その周辺が最も不自然に見えるため",
  "hypotheses": ["欠け", "汚れ付着", "照明反射による偽陽性"],
  "checks": ["該当箇所を拡大してエッジ形状を確認", "照明条件を変えて再撮影して再推論", "良品画像と並べて比較"],
  "false_positive_risk": "medium",
  "notes": "反射っぽいハイライトが近くにあるため断定は避ける"
}
```
